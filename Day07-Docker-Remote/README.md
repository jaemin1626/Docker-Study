# Docker 컨테이너를 통한 서버 간 원격 통신

MLOps Server와 Train Server 예시를 통해 서로 다른 컴퓨터의 Docker 컨테이너가 요청을 받고 응답하는 원리를 정리합니다. 구현 코드나 학습 파일 구성 대신, 대화에서 다룬 통신 개념에 집중합니다.

## 1. 전체 구조

| 구분 | IP | API 포트 | 역할 |
| --- | --- | --- | --- |
| MLOps Server | `172.16.4.86` | `8000` | 사용자 요청을 받고 Train Server에 학습 요청 전달 |
| Train Server | `172.16.4.85` | `9000` | 요청을 받아 학습 실행 및 상태 응답 |

```text
MLOps Server (172.16.4.86)
┌──────────────────────────────────────┐
│ Docker 컨테이너: MLOps API            │
│ Train API로 HTTP 요청 전송            │
└──────────────────┬───────────────────┘
                   │
                   │ POST http://172.16.4.85:9000/train
                   ▼
Train Server (172.16.4.85)
┌──────────────────────────────────────┐
│ 호스트의 9000 포트                    │
│            ↓ 포트 매핑               │
│ Docker 컨테이너의 9000 포트           │
│            ↓                         │
│ Train API가 요청 처리                │
└──────────────────┬───────────────────┘
                   │
                   └── 기존 HTTP 연결을 통해 응답 반환
```

Docker는 애플리케이션을 실행할 환경과 네트워크 구성을 제공합니다. 실제 요청을 받아 기능을 수행하고 응답하는 주체는 컨테이너 안에서 실행 중인 API 서버입니다.

## 2. 두 서버를 미리 연결해야 하나요?

별도의 Docker 연결을 두 컴퓨터 사이에 미리 만들어 둘 필요는 없습니다. Train API를 실행해 요청을 받을 수 있는 상태로 두고, MLOps가 필요할 때 해당 IP와 포트로 요청합니다.

```text
평소: Train API가 지정된 포트에서 요청 대기
요청 발생: MLOps → Train Server의 IP:포트로 접속 → API 호출 → 응답 수신
```

서버 사이의 네트워크 경로가 존재하고 방화벽이 접근을 허용해야 합니다. HTTP 연결 생성이나 재사용은 클라이언트와 네트워크 계층이 처리합니다.

## 3. 컨테이너에 포트를 부여하면 바로 접근할 수 있나요?

포트 번호를 정하는 것만으로는 충분하지 않습니다. 일반적인 Docker bridge 네트워크에서는 다음 조건이 필요합니다.

1. 컨테이너 안에서 API 서버가 실행 중이어야 합니다.
2. API가 외부에서 전달된 요청을 받을 수 있는 주소에 바인딩돼 있어야 합니다.
3. 호스트 포트를 컨테이너 포트로 공개·매핑해야 합니다.
4. 네트워크 경로와 방화벽이 접근을 허용해야 합니다.

포트 매핑을 다음과 같이 설정하면 호스트의 `9000` 포트가 컨테이너의 `9000` 포트로 연결됩니다.

```yaml
ports:
  - "9000:9000"
```

```text
172.16.4.85:9000 → 컨테이너:9000 → API 서버
```

왼쪽은 호스트 포트, 오른쪽은 컨테이너 포트이며 두 번호가 반드시 같을 필요는 없습니다. `EXPOSE`만으로 외부 접근이 열리지는 않습니다. 관련 동작은 [Docker 포트 공개 문서](https://docs.docker.com/engine/network/port-publishing/)를 참고하세요.

### 0.0.0.0과 localhost

컨테이너 안의 API가 `0.0.0.0:9000`에서 대기하면 컨테이너의 모든 네트워크 인터페이스에서 요청을 받습니다. `0.0.0.0`은 대기 설정에 사용하는 주소이며, 다른 서버가 접속할 목적지 주소가 아닙니다.

MLOps는 Train Server의 실제 주소로 요청합니다.

```text
http://172.16.4.85:9000/train
```

MLOps 컨테이너에서 `localhost`는 그 컨테이너 자신을 가리킵니다. 다른 컴퓨터의 Train Server를 가리키지 않습니다.

같은 Docker 네트워크에서는 서비스 이름으로 접근할 수 있지만 서로 다른 컴퓨터의 기본 Compose 네트워크가 자동으로 연결되는 것은 아닙니다. [Compose 네트워킹 문서](https://docs.docker.com/compose/how-tos/networking/)에서 범위를 확인할 수 있습니다.

## 4. 요청이 들어오면 어떤 순서로 처리하나요?

예를 들어 MLOps가 다음 요청을 보냅니다.

```http
POST /train HTTP/1.1
Host: 172.16.4.85:9000
Content-Type: application/json

{"model":"yolo","epochs":100}
```

```text
MLOps에서 요청 전송
        ↓
네트워크·방화벽 정책에 따라 Train Server까지 전달
        ↓
호스트 포트에서 컨테이너 포트로 전달
        ↓
API가 경로와 HTTP 메서드에 맞는 처리 함수 선택
        ↓
접속 IP·인증 정보·요청 데이터 확인
        ↓
허용된 기능 실행
        ↓
HTTP 응답 반환
```

컨테이너가 임의의 요청을 알아서 처리하는 것은 아닙니다. `POST /train`을 받았을 때 수행할 기능은 API 코드에서 정의합니다.

## 5. 요청자의 IP로 결과를 다시 보내야 하나요?

일반적인 HTTP 요청에서는 요청자의 IP를 읽어 새 연결을 열 필요가 없습니다. 처리 함수가 결과를 반환하면 API 서버가 기존 요청에 대한 응답으로 전달합니다.

```text
MLOps ── HTTP 요청 ──▶ Train API
MLOps ◀─ HTTP 응답 ─── Train API
```

반환 데이터 예시:

```json
{
  "status": "accepted"
}
```

접속 IP는 접근 허용 여부를 판단하거나 로그를 기록하는 데 사용할 수 있습니다. 응답을 전달하기 위해 애플리케이션이 목적지 IP를 다시 지정할 필요는 없습니다.

## 6. 학습이 오래 걸리면 어떻게 응답하나요?

수 시간 걸리는 학습에서는 작업을 접수한 뒤 `job_id`를 빠르게 반환하고 학습을 별도로 진행할 수 있습니다.

```text
MLOps → POST /train → Train API
MLOps ← job_id와 접수 상태

Train Server에서 학습 진행

MLOps → GET /train/{job_id}/status → Train API
MLOps ← 현재 작업 상태
```

접수 응답 예시:

```json
{
  "job_id": "job-1234",
  "status": "queued"
}
```

상태 조회 주소:

```text
GET http://172.16.4.85:9000/train/job-1234/status
```

조회 응답 예시:

```json
{
  "job_id": "job-1234",
  "status": "running"
}
```

| 상태 예시 | 의미 |
| --- | --- |
| `queued` | 접수 후 실행 대기 |
| `running` | 학습 진행 |
| `completed` | 학습 완료 |
| `failed` | 학습 실패 |

이 API 경로와 상태 이름은 설계 예시입니다. 작업 ID 생성, 학습 실행과 상태 저장은 애플리케이션에서 구현합니다. 접수 응답은 학습 완료를 의미하지 않습니다.

### 완료 알림을 먼저 보내는 경우

Train Server가 완료 시점에 MLOps에 알리려면 callback 또는 webhook을 별도로 구현합니다.

```text
최초 요청: MLOps → Train → 접수 응답
학습 완료 후: Train → MLOps의 완료 알림 API로 새 HTTP 요청
```

완료 알림은 최초 요청의 `return`이 아니라 새로운 요청입니다. 따라서 접근 가능한 MLOps API 주소와 포트, 역방향 접근 허용과 인증이 필요합니다. 최초 연결이 종료된 뒤 그 응답을 다시 보내는 방식은 아닙니다.

## 7. IP 제한과 방화벽은 어떤 역할인가요?

| 구분 | 역할 | 예시 |
| --- | --- | --- |
| 방화벽·네트워크 정책 | 요청이 목적지까지 도달할 수 있는지 제한 | Train의 9000 포트에 MLOps IP만 접근 허용 |
| API의 IP 검사 | 도달한 요청의 접속 주소를 검사 | 허용되지 않은 주소에 403 응답 |
| API 인증 | 요청 주체와 권한 확인 | 토큰 또는 인증서 검증 |

방화벽에서 차단되면 API 함수까지 요청이 도달하지 않을 수 있습니다. API 코드에서 거부하면 HTTP 오류 응답을 반환할 수 있습니다. IP 제한은 인증을 대신하지 않습니다.

API가 확인하는 접속 IP는 NAT 또는 프록시 구성에 따라 실제 요청 서버의 IP와 다를 수 있습니다. 전달 헤더에 적힌 IP를 무조건 신뢰하지 말고 실제 네트워크 구성에 맞게 판단해야 합니다.

## 8. SSH 원격 접속과 API 통신은 어떻게 다른가요?

여기서 설명하는 원격 통신은 상대 서버의 API를 호출하는 방식입니다. SSH로 서버나 컨테이너 안에 들어가 명령을 실행하는 방식과는 역할이 다릅니다.

| 방식 | 용도 |
| --- | --- |
| SSH | 운영자가 서버에 접속해 명령 실행, 배포, 로그 확인 등 관리 |
| REST API | 서비스가 미리 정의된 기능을 요청하고 응답 수신 |

MLOps가 학습 API를 호출할 때 SSH 접속을 먼저 할 필요는 없습니다. Train API가 실행 중이고 네트워크 접근이 허용돼 있으면 HTTP로 요청할 수 있습니다. SSH 연결을 종료해도 실행 중인 API 서비스는 계속 요청을 받을 수 있습니다.
